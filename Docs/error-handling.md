# Error Handling & Diagnostics

This document outlines the centralized exception handling architecture, RFC 7807 compliance, database constraint translation, and diagnostic health checks in the **URL Shortener API**.

---

## 1. Centralized Global Exception Handling

The API implements ASP.NET Core's [`IExceptionHandler`](file:///home/saadm/Data/C#/Url_Shortner/Exceptions/GlobalExceptionHandler.cs) pipeline to intercept, translate, and format all uncaught exceptions uniformly.

### Registration in `Program.cs`
```csharp
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
...
app.UseExceptionHandler();
```

## 3. RFC 7807 ProblemDetails Response Format

Every error returned by the API adheres to the standard RFC 7807 specification:

```json
{
  "type": "https://httpstatuses.io/404",
  "title": "Not Found",
  "status": 404,
  "detail": "Url '999' was not found."
}
```

### Response Attributes:
- `type`: URI reference identifying the problem type (points to `https://httpstatuses.io/{code}`).
- `title`: Short, human-readable summary of the problem type.
- `status`: The HTTP status code generated by the origin server.
- `detail`: A human-readable explanation specific to this occurrence of the problem.

## 4. Logging & Diagnostics Strategy

The exception handler applies appropriate log levels based on HTTP status:
- **Client-side errors (`4xx`)**: Logged at `LogLevel.Warning` to minimize noise while tracking operational issues.
- **Server-side faults (`5xx`)**: Logged at `LogLevel.Error` with full stack traces for root-cause diagnosis.
